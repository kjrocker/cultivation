# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A static SPA body-cultivation planner for the game _Amazing Cultivation Simulator_. It reads the game's shipped XML settings files, flattens them into a queryable data model, and lets the user build a cultivator (species, body law, tempered parts, quenching labels, secret bodies) while showing the resulting property/modifier totals.

Package manager is **yarn** (`.yarnrc.yml`, `nodeLinker: node-modules`, `engine-strict=true`). CI runs `yarn install && yarn test:ci`.

## Commands

```bash
yarn dev                 # vite dev server
yarn build               # static build -> ./build (deployed to GitHub Pages)
yarn preview             # serve the production build on :4173

yarn test                # vitest watch mode (unit tests colocated in src/**/*.test.ts)
yarn test --run src/lib/util/format-number.test.ts   # single file
yarn test --run -t "substring of test name"          # single test
yarn test:ci             # lint + vitest --run  (what CI runs)

yarn lint                # prettier --check + eslint
yarn format              # prettier --write
yarn check               # svelte-check against tsconfig.json

yarn e2e                 # playwright (builds + previews first)

yarn json                # regenerate static/Data/*.json from ACS/ XML — see below
./makeList.sh            # regenerate src/types/settings.ts + src/types/language.ts
```

`yarn e2e` needs browsers once: `npx playwright install chromium`. It is not part of `test:ci`.

## Architecture

### The base path is load-bearing

`svelte.config.js` sets `paths.base = '/cultivation'`, and that prefix is **hard-coded** in the one runtime fetcher, `src/lib/data/util/write-json.ts` (`read()` fetches `/cultivation/Data/*.json`). `src/hooks.ts` disables SSR entirely and `adapter-static` uses `fallback: 'index.html'`, so this is a pure client-side SPA. Anything touching URLs must keep those three in sync.

### Data pipeline: XML → JSON → stores

Game data flows through three stages. Understanding this is the main thing:

1. **XML under `ACS/Settings/`** — verbatim game files, plus an English translation tree under `Language/OfficialEnglish/Settings/`. This tree lives _outside_ `static/` deliberately: `static/` is Vite's publicDir and is copied verbatim into `build/`, so XML kept there ships 156M of never-requested files to production. It is a build input only. `src/types/settings.ts` and `src/types/language.ts` are string-union types listing every available file, generated by `makeList.sh` from that directory tree — never hand-edit them (`makeList.sh` output needs `yarn format` after).

2. **`src/lib/data/xml/get-*.ts`** — one reader per domain (body parts, labels, secret bodies, modifiers, body laws, essence names). Each calls `getSettings()`/`getLanguage()` from `data/api/get-data.ts` — a **node-only** reader (`fs.readFile` off `./ACS/…`; there is no browser path, by design) which parses XML with `fast-xml-parser` (attributes prefixed `@_`, exported as `A_PREFIX`). Translation is applied by `joinEnglishPaths()`, which converts the language file's dotted path keys into Ramda lenses and `set`s English strings onto the parsed settings object. Readers then flatten nested `<Parts>` trees, strip `@_` prefixes, and finish with `createDataView(list, 'Name')`.

3. **`static/Data/*.json`** — precomputed output. `createDataReader(name, fn, shrink, expand)` in `data/util/write-json.ts` gives each reader two halves: `write()` runs the XML parse in Node and dumps JSON (only reachable via `yarn json` → `data/dump-to-json.ts`), and `read()` runs in the browser and just fetches the JSON, then `expand()`s it. **The browser never parses XML** — it only reads `static/Data/*.json`. So after editing any `get-*.ts` reader or any XML under `ACS/`, you must run `yarn json` and commit the regenerated JSON, or the app keeps serving stale data. `yarn json` runs the script through **tsx** — not `ts-node`, which could not resolve this codebase's extensionless imports under `"type": "module"` on modern Node.

### DataView keys are stable IDs

`createDataView` produces `{ keys, list, map }`. `shrink`/`expand` drop `list` to save bytes, and — more importantly — **backup/restore encodes user selections as indices into `keys`** (`components/backup-restore/util.ts`, `stores/minified-cultivator.ts`, base64 of a `MinifiedOptionsV2` blob). Reordering or removing entries in the source XML changes those indices and silently invalidates every previously exported cultivator code. `minified-cultivator.ts` carries V1/V2/V3 shapes; the export form currently writes V2.

### Store layering

Three tiers, all Svelte stores:

- **Static data** (`src/lib/data/stores.ts`) — `createStaticAsyncStore` wraps each reader's `read()`; the store starts `null` and is filled by `init()`. `+layout.svelte` awaits all six `init()` calls and renders nothing until they resolve, so downstream code can assume they are populated.
- **User state** (`src/lib/components/stores/`) — writables with custom APIs: `options-store` (species/law/tempering toggles), `part-label-count-store` (the per-body-part quenching labels, keyed by part name), `equipped-secret-bodies-store`, `selected-store`.
- **Derived** — everything else in that folder (`current-properties-store`, `current-modifiers-store`, `global-body-bonuses-store`, `qi-recovery-balance-store`, `complete-secret-bodies-store`) is `derived(...)` over the two tiers above. Computation lives here, not in components.

Static tuning tables that aren't in the game XML live in `src/lib/data/`: `species.ts` (species → XML file mapping + excluded part names), `property-config.ts` (display names, percentage/rate formatting, caps), `tempering-config.ts` (label inheritance rules folded in by `get-labels.ts`).

## Conventions

- Heavy **Ramda** use throughout (`pipe`, `lensPath`, `mapObjIndexed`, `indexBy`, `renameKeys` from ramda-adjunct). Match that style in data-transform code.
- Files are kebab-case; components are lowercase `.svelte` under `src/lib/components/`, with generic primitives in `base/`.
- Tabs, single quotes, no trailing commas, 100 cols (`.prettierrc`). `static/` is prettier-ignored.
- XML-shaped intermediates are deliberately `any`/`@ts-expect-error` inside the readers; the typed boundary is `src/lib/data/types.ts` (`BodyPart`, `LabelView`, `SecretBody`, `Modifier`, …).
- Dark mode is done with Tailwind `dark:` classes plus `prefers-color-scheme` blocks; there is no theme toggle.
